# DSH mobile session and profile validation

This is an isolated validation prototype for the fixed `@deepseek-ai/dsh-api-session-controller` `0.2.2-alpha.3` dependency. It does not add a production route, launch another DSH process, access a user's Session, call a model, or read provider/MCP credentials. The controller and ledger are injected; tests use a fake command/state/history surface.

## What the pinned DSH surface provides

- `SessionController.prompt(request, signal)` validates prompt content and sets `source.rpcId` to the client `requestId` before calling its command controller. The command implementation checks the live Agent inbox and persisted Session events for that request ID before admitting a duplicate. This is Host-side request correlation; it does not prove exactly-once model execution or fingerprint checking. See `node_modules/@deepseek-ai/dsh-api-session-controller/lib/index.js` around `SessionController.prompt`, `SessionCommandController.prompt`, and `hasPromptRequest`.
- `SessionController.state({sessionId})` is a passive read with cursor, running/active state, queue, and pending input kinds. `cancel({sessionId})` returns whether cancellation was admitted; it is not a terminal stopped result.
- `SessionController.events({address, throughSeq, beforeSeq, maxMessages})` returns chronological raw event entries at a fixed cut and indicates whether older records remain. The `seq` is retained as the event cursor. `follow` opens a snapshot and then streams uncovered history; the DSH client event-stream adapter handles continuity repair/reconnect.
- The exported `skills.list({sessionId})` remote method provides human-invocable skill metadata, not skill bodies.
- `agentPresets.list()`, `agentPresets.read(id)`, and `agentPresets.select(sessionId,id)` expose the preset roster, declared composition document, and blank-session preset selection. The document is composition YAML, not a resolved mobile persona snapshot; selection is locked once the Session conversation starts.

The pinned DSH packages do not expose a general `SOUL.md` / `USER.md` / memory snapshot Remote API or a generic MCP server/tool catalog API. Shiwen's profile snapshot therefore comes from the existing authenticated `shiwenLibrary.agentState()` data, not from arbitrary DSH presets. The host workbench's authenticated `mobileAgentProfile` RPC now calls this snapshot adapter; the DSH session prototype itself remains unwired to the Remote Gateway.

## Shiwen profile snapshot contract

`createProfileSnapshot(state, {agentId})` accepts `shiwenLibrary.agentState()` output and returns:

```js
{
  version: 1,
  agentId,
  systemContext: "...",
  documents: [{name: "IDENTITY.md"|"SOUL.md", body, revision}],
  memories: [{id, body, category, revision, updated}],
  included: {globalActiveMemories, memoryContextEntries, memoryContextOmitted},
  revision: "sha256"
}
```

`systemContext` is generated by the existing `personalContext(state)` function, so mobile uses the exact same identity + SOUL + active global memory wording and 1,800 UTF-16-unit injection budget as desktop. In addition, the snapshot carries the two identity document bodies and every active global memory body so the mobile copy can retain memories that the desktop prompt budget currently omits; `included` reports total transferred and prompt-injected/omitted counts. Pending, rejected, deleted, and project-scoped memories are excluded. Policy, configuration documents, events/audit rows, evidence/source columns, tools, capability permissions, and secrets are never copied. `agentId` must be `shiwen`; the adapter rejects relabeling another DSH preset as Shiwen. It rejects `systemContext` over 32,000 UTF-16 code units and a JSON response over 256 KiB with `PROFILE_TOO_LARGE`; it never silently truncates. The SHA-256 revision covers the normalized snapshot content and agent identity, not transport time or local node identity. The host route must key/cache by node and agent and enforce caller/node access.

## Prototype behavior and verification boundary

`createMobileSessionAdapter({controller, ledger})` demonstrates conservative client behavior:

- persisting a request hash before sending; a repeated ID with altered prompt content is rejected;
- treating a prompt transport error as `unknown`, then reconciling through passive state/event reads without automatically resending;
- preserving event sequence values and flagging duplicate events or gaps;
- representing cancellation as `cancel-requested`, not `stopped`;
- surfacing pending approval/question input as user work and exposing no auto-approval method.

The included tests call the actual pinned `SessionController.prototype.prompt` wrapper with an injected fake command fixture. State, events, cancel, the ledger, and profile state are fixtures. They do not execute DSH's full Cordis Host composition, generated Remote transport, actual inbox/persistence duplicate detector, live Agent lifecycle, Android transport, or any model/tool invocation. The profile tests verify a whitelist over a synthetic `agentState`; the real authorized Shiwen workbench RPC has been connected and tested with an isolated actual Shiwen library. Android MockWebServer tests additionally validate password login, encrypted remembered sessions, profile hashes using a JS-generated fixture, and preservation of the last profile when refresh fails. A real running DSH host and Android LAN connection remain separate acceptance gates.

Run only these isolated tests with:

```sh
node --test tests/mobile-session-adapter.test.mjs tests/mobile-profile-adapter.test.mjs
```

The profile route uses the authenticated owner session; the remote peer/node binding and client cache key must still keep snapshots isolated by node. Production session admission still needs a durable mobile request ledger, end-to-end session-stream reconnect coverage over the real DSH Remote Gateway, an explicit capability metadata API, and UI handling for user-required interactions. No approval, secret transfer, full DSH profile download, or exactly-once model guarantee is claimed here.
