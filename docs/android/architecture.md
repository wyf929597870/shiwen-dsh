# 移动资料库架构决策与生命周期

日期：2026-11-06。状态：第一种架构已由用户确认；下述实现合同尚未落地，P0 冻结字段与依赖版本。本文定义架构与生命周期，[同步协议](sync-protocol.md) 定义数据操作，[实施计划](README.md) 定义阶段，[页面流程](ux-flows.md) 定义交互。

## 1. 已决定的架构

**本地优先、完整多副本、可替换的中心协调服务。** 同一个 libraryId 的每个完整客户端独立保存资料、检索、编辑并运行其可用的本机 AI；联网时通过该库当前选定的协调服务汇合修改。客户端不直连彼此交换数据，也不自动选举协调者。

协调服务可运行在本机电脑或局域网另一台主机。多个节点可以服务多个不同资料库；同一资料库同一客户端只认一个当前协调身份。网络分区时无法阻止另一群尚未获知迁移的设备继续使用旧服务，恢复流程必须保存并对账两边分支，不声称通过一个 epoch 字段实现分布式共识。

| 参与者 | 数据与责任 | 离开协调服务后 |
| --- | --- | --- |
| Android 完整客户端 | 持久资料库、版本/活动/删除状态、附件、同步队列、本机工具和可选模型配置 | 继续本地读写；联网模型可独立调用；等待恢复同步 |
| PC 独立服务及其库 | 完整持久库、DSH Agent、统一提交、同步日志/回执、设备进度 | 原库仍可本机使用；停机不清除客户端资料 |
| 当前桌面外壳/浏览器 | 连接所选服务并显示 Web 页面 | 仅打开远端页面不自动产生完整副本；浏览器缓存不能作为恢复源 |
| 未来 iPad 等完整客户端 | 复用协议并实现各平台本地持久化与调度 | 产品目标同 Android，但本次不交付 iOS 工程 |

“每端有完整资料库”指参加复制的完整客户端与服务持久库，不包括单纯打开网页的浏览器标签。桌面连接远端时若未来也要求独立副本，须接入同一复制引擎并单独验收，不能由当前外壳能力推断已支持。

最终一致的条件：同库同代次、传输成功、初始化和所需文件完整、操作已对账、冲突已处理；所有参与端处理到同一个有限切点后得到一致状态。持续编辑时只能声明“截至切点 H”，不能声明永远实时一致。

## 2. 完整范围与最小分层

每库完整范围：正文、可写元数据、来源分段、记录关系、当前保留政策下的版本与回收站、活动统计、库内附件和导入原件。最近 7/14/30 天仅是查询条件，不是保存范围；没有历史正文自动淘汰模式。外部链接不表示镜像网站，已经被旧系统清除的历史也不能补造。

按 2026-11-06 用户确认，节点认证后自动拉取所选 Agent 的人设、用户偏好和已确认记忆，按节点与 Agent 隔离保存完整快照，供新会话使用；这与资料库同步分别报告。会话档案上传仍须独立开关，“完整资料库”不隐式开启会话上传。模型凭据、登录状态、运行中的 Agent 进程、工具执行权限和设备文件绝对路径不参与资料同步。技能与 MCP 可用能力清单可以同步展示，配置同步不自动授予手机执行权限。具体规则见 [完整交付清单](delivery-board.md)。

| 拟定模块/接口 | 承担 | 不承担 |
| --- | --- | --- |
| LocalLibrary / Repository | 本地事务、查询、版本、活动、操作回执、资料工具统一写入 | 不要求服务可达后才允许保存 |
| ChangeJournal | 稳定变更身份、来源设备、修改基线与不可变内容，供对账/恢复 | 不把服务游标当作业务身份 |
| ReplicaEngine | outbox、先查回执、增量应用、完整性和冲突 | 不另建第二套 UI 写库或模型生成任务 |
| CoordinatorTransport | 认证、能力协商、批次/附件传输、当前协调代次 | 不决定正文合并策略，不持有可变“当前库” |
| Bootstrap / RecoverySession | 完整快照、同库首次启用、换协调服务、其他副本再加入 | 不复用跨库导入的 ID 重建逻辑 |
| BlobStore / Backup | 库内对象校验、临时发布、完整备份和恢复 | 不用缓存清理删除唯一资料 |

这是职责拆分，不要求每个接口单独拆包或进程。Android 原生 repository 负责唯一事务边界，UI、手动同步、WorkManager 和本机 Agent 都调用它；服务端依然只有一个资料库写进程。

## 3. 生命周期与本地状态

registry 保存两个独立维度：连接角色 `standalone / coordinated / paused / rebind-required`，副本完整性 `initializing / complete / incomplete`。同步任务状态、冲突数、待传输数另存。`complete` 表示完整到一个已校验切点，不代表没有新编辑或未知远端变化。

| 场景 | 动作 | 不变量 |
| --- | --- | --- |
| 只用手机 | 创建 standalone 库，直接记录与配置模型 | 本地写入和回顾无服务依赖，不出现虚假待同步 |
| 电脑先建 | 手机获取原 libraryId 的一致快照，再拉增量 | 记录/版本/活动身份保留；完整前显示初始化进度 |
| 手机先建 | 选择空的已授权目标，在暂存区上传完整快照并提交 | 同库原身份和历史保留，手机继续使用原数据库 |
| 手机先建期间仍编辑 | 固定切点快照，后续编辑保留为 successor | 提交基线映射后对账上传，不能用快照覆盖后续编辑 |
| 新地址与已有库同身份 | 重新认证、核对协调代次后复用本地库 | 不重复创建数据库，不迁移原地址 Cookie |
| 新服务已有不同库 | 作为独立库添加；另提供显式跨库复制 | 不根据相似名称/正文自动合并 |
| 服务暂时不可达 | 保留当前绑定，继续本地写入、退避重试 | 不因一时离线启动接管或另建资料库 |
| 永久停用一个客户端 | 有机会时先同步；本地删除是独立操作 | 不向其他设备发布全库删除 |
| 暂时不再同步 | paused 保留库、基线和队列；恢复时先对账 | 不能丢弃 pending 来制造 standalone 的“干净”状态 |
| 协调服务已丢失 | 用户发起恢复，选择完整存活副本与新服务 | 新服务可能比其他端旧，不能强制覆盖它们 |

初次接入只允许空目标发布，或明确进入维护状态的同库恢复目标；不能让客户端任意提交服务器文件路径。服务配置允许接收的库位置与库角色，密码会话鉴权后再验证该操作能力；新增服务仍按现有方式由主机所有者设置访问密码。已占用不同库的服务应另启空配置/实例，本轮不顺带引入一个服务承载多个库。

## 4. 首次启用与协调服务恢复

统一采用持久 setup 任务：`preparing → receiving → verifying → ready → committed`；失败可重试，提交前可 abort，提交后的取消不能撤销已发布资料。setupId 与请求指纹固定，提交响应丢失先查 status；不能重建一份库。

1. 选择来源快照与目标，核对 libraryId、任务种类、来源完整性、预计空间。缺文件的来源不能标为完整恢复；允许保存不完整候选供汇集缺项，但只能留在 rescue 暂存区，不得发布为正常可写协调库。
2. 传输到隔离暂存区；各页/块有散列、大小和持久进度。任务绑定已认证所有者及库，重新登录后重新授权才能续传；不把 setupId 当凭据。
3. 校验清单、关系、版本/活动身份和全部附件。原来源仍可使用，后续修改保留，staging 不与运行中的库混写。
4. setup 创建时原子预留目标，记录目标 generation、库身份/epoch、任务所有者及递增 fencingToken；同一目标只允许一个有效任务，其他任务返回 SETUP_TARGET_BUSY。发布前短暂停止目标库普通写入，在同一门禁内重新校验预留、令牌、generation、目标仍为空或为获准停写的同库，CAS 成功才原子切换完整 manifest/数据库指针并递增 generation；文件对象须先落盘，失败保持旧指针。不能假设 SQLite 事务与任意文件 rename 是同一个事务。崩溃时根据持久状态恢复，最终 commit 回执与发布指针必须一致。
5. 手机首次启用：生成初始服务 revision 映射，保留业务版本/活动 ID 与库时区，不将历史导入当天计数。来源手机接收回执后更新绑定/基线，再发送期间的 successor。
6. 更换协调服务：生成新 syncEpoch，保留 libraryId、业务版本和来源链；更新 serverId 与认证，不搬运旧登录身份或信任旧服务令牌。显示“恢复到切点 H，其他设备待汇合”。

预留为可续期持久租约。租约失效后旧 worker 不能发布；原任务恢复也须重新授权、重新取得递增令牌并核对目标 generation，不能仅凭旧 ready 状态提交。已提交任务的相同 commit 重试先返回持久回执，不因 generation 已增长而误报失败；未提交且目标已变化返回 SETUP_TARGET_CHANGED，保留暂存数据供重新评估。续期/释放/abort 都校验当前任务和令牌，不能解除别人的预留。服务重启保留 fencing 计数与发布结果，过期租约不得自动复活。

不完整来源进入 `receiving + rescue`，可只读预览/导出已有内容并展示缺项；不开放普通同步、Agent 写入或完整确认。仅从明确授权的同库来源补齐并验证一致切点、关系与历史后才进入 ready；不同分支不能按文件凑齐，须先保留并裁决。取消仅释放本任务预留并停止传输，候选和原来源保留；清理候选需独立明确操作。不提供自动删除缺失引用、带缺项强制发布或一键另建库绕过校验。

同一 service 的 setup 发布与其他写入口必须共用维护门禁。移除 staging 只影响未发布临时对象；共享对象或被当前版本/历史引用的附件不得清理。

### 其他端重新加入

恢复不能只重放 outbox。例如：安卓 A 的修改已经被旧服务确认，A 的队列为空，但用于恢复的平板 B 还未下载它。A 重连时必须提交旧代次的版本清单和差异，不能被 B 的旧快照覆盖。

- 重新登录并确认新协调身份；保留原库、已确认基线、所有本地版本、操作回执、冲突和待处理链。
- 新建 reconcile 任务，交换版本/来源清单；原 changeId 与 versionId 作为同一内容的识别依据，旧 revision/seq 仅作来源记录。
- 相同版本直接映射；可证明为同一基线后继且无其他分支时提交保留历史的恢复操作；分支并发或缺少可证明共同基线时保存双方进入显式冲突。时间戳、版本整数大小或正文相同都不能单独证明谁覆盖谁。
- 不存在于恢复快照的记录不视为已删除：比较 tombstone 与历史链。删除/恢复相遇保留双方，不能用“对端没有”自动删本地内容或复活旧记录。
- 使用新代次 envelope 提交，但保留原变更/活动身份防重。新服务确认后才结束对应旧待处理项，其他后继编辑继续保留；恢复性提交不制造写作统计。
- 汇合结果和完整性检查持久化后解除该库 rebind-required。其他尚未重连设备显示“最后确认于旧代次”，不能显示全体已一致。

### 同一协调代次内换机

新安装恢复原库后使用新的 deviceId，先登记并由库所有者授权 `device-restore` 汇合任务；即使 serverId/epoch 未变也必须执行。任务限定库、来源设备与备份清单，可按 changeId/versionId/活动身份核对已应用内容，并在该任务内映射旧操作的确切回执；普通 receipts 接口仍不能查询他人的设备。ACK 丢失但已应用的旧变更只确认映射，未应用的保留原业务身份，经恢复授权以新安装 envelope 提交；未知结果不等于未执行。新设备不继承旧凭据，来源字段也不授予旧设备权限。活动以 `(libraryId, activityId)` 去重，originDeviceId 是不可变来源，不随提交设备改变。旧手机稍后上线时仍按相同业务身份去重，后续分支按基线裁决；发现撤销需求由所有者单独停用旧设备。

### 旧服务重新出现

用户切换到新协调身份后，客户端拒绝旧代次普通 push/pull；旧服务数据可作为恢复候选来源显式汇合。未获知切换的设备可能产生旧分支，纳入上述 reconcile。不得通过自动比较“更大的 epoch”选主，epoch 是身份而不是全球递增时钟。迁移完成后由所有者停用旧写入口；不能远程撤销一台不可达主机上的所有历史凭据。

## 5. 稳定变更身份与未来可复用部分

v1 保留三类不同编号：

- **业务身份**：libraryId、recordId、versionId、changeId、活动 ID；创建端生成后持久保存，传输/恢复不改。versionId 标识一个不可变业务状态，changeId 标识一次正式业务变更；合并产生新身份并引用被裁决版本。
- **来源与基线**：originDeviceId、baseVersionId（合并时记录 parents）、规范内容散列、原发生时间。服务端 legacy 数据迁移时一次性建立身份并持久化，未知设备留空，不能伪造历史作者。
- **协调编号**：syncEpoch、revision、seq/cursor 只在当前协调代次内有排序意义；operationId 标识本代次传输请求，重试请求体不可变。换代次时创建新的传输 envelope，原 changeId/业务载荷不变；冲突解决改变业务内容时创建新 changeId，而不是给旧请求换正文。

普通客户端只能提交其已授权的创建设备变更；恢复任务可在明确授权下保留其他设备历史来源，但来源字段不授予那台设备的权限。不要为了未来扩展放开当前写入校验。

| 将来转成对等同步 | 当前处理 |
| --- | --- |
| 本地完整存储、资料工具、内容格式、变更身份、附件散列 | 现在完成并保持与传输独立，可复用 |
| 认证、断点传输、幂等、冲突保留界面 | 分层封装，可复用部分实现与故障样例 |
| 变更先后/并发判定、删除传播、收敛和全网去重 | 当前由协调端排序；将来需要重做跨端因果关系和合并协议 |
| 节点发现、直连/中继、多端授权、移动后台连接 | 当前只连接所选服务；将来另行设计和真机验证 |
| 日志压缩、设备退役、长期离线设备回归 | 现在保守保留并观察占用；对等版本需重新定义安全回收条件 |

不预先实现 CRDT、区块链、向量时钟、自动选主或抽象传输插件市场。保留稳定身份和边界是减少迁移成本，不是承诺对等同步可直接开关启用。

## 6. 换机、备份、恢复与保留

这是完整手机资料库的发布要求，不以“已经同步”取代备份：

- **Markdown 导出/导入**：正文与可移植元数据、附件相对引用；用于开放格式交换，不声称保留全部历史。导入预览类型/日期/来源与重名项，保留原件；不能直接复制 SQLite 作为跨平台导入。
- **完整备份包**：版本化 manifest、库身份/时区、记录/版本/关联/活动/删除状态、库内对象、该设备草稿与未同步分支、用户选择的会话/记忆。登录凭据、模型 Key、签名私钥不导出。只含同一一致切点的业务快照，同时记录后续未同步变更边界。
- **备份存放**：由用户选择本机外部文件位置或自行保管的介质，不自动上传云。暂存包完成校验后再发布，不覆盖唯一可用备份；可选加密完整包，采用成熟库与可移植口令方案，P0 冻结格式与依赖，不手写密码学。
- **换机恢复**：校验格式、散列、引用和空间，在暂存库恢复并原子启用；保留 libraryId/业务身份，新生成安装 deviceId，凭据重新配置。旧设备未确认操作不能直接换 deviceId 冒充新上传，必须走恢复对账映射；同库业务变更按 changeId 去重；同一服务/epoch 内换机也执行 device-restore 汇合，历史 activityId/originDeviceId 不改。
- **恢复用途**：提供“恢复原库”与“导入为新库”两种明确操作，后者生成新库身份且不继承同步绑定。运行中的同库存在内容时先预览差异，禁止覆盖待处理修改。
- **历史保留**：同步 v1 不自动清理 tombstone、未确认回执、冲突分支或库内原件。磁盘不足暂停并提示备份/管理容量；只清理无任务引用且未发布的过期 staging、可重建索引/缩略图。未来压缩需另定义设备确认与过期规则，不能靠删除历史正文满足空间预算。

完整备份的成功标准是能在干净安装中恢复并核验，不能只检查文件存在。可选加密包还需验证错误口令、损坏包与中断失败保持原库可用。

## 7. 发布前必须通过的架构场景

| 场景 | 验收结果 |
| --- | --- |
| 手机不配置任何服务连续使用 | 本地记录/搜索/创作/回顾可用，模型联网后独立运行 |
| 电脑先建、手机先建两种顺序 | 同库加入后 ID、版本、活动和附件一致，无重复统计 |
| 一个协调服务、两个独立副本 | 任意顺序离线修改/上线，处理冲突后切点一致 |
| 上传 ACK 丢失、初始化 commit ACK 丢失 | 查询原请求/任务，无重复保存或重复建库 |
| 协调服务突然丢失 | 两个副本可独立使用，直到用户恢复新服务前不假装互相同步 |
| 用较旧副本恢复，另一端有旧服务已确认的新记录/删除 | 全分支对账找回差异，非空 outbox 不是恢复前提 |
| 初始化/恢复期间再次编辑或存储满 | 保留 successor 与原库，完整性不足不发布成功 |
| 旧服务及长期离线客户端回归 | 新绑定不回退；旧分支显式汇合，无静默覆盖 |
| 用户切库，旧连接/后台任务晚返回 | 只更新原 LibraryContext，不串库或串凭据 |
| 各端数据不同但服务已接收一批上传 | 展示真实确认切点，不显示所有设备已备份 |
| 备份换机、重复恢复、损坏备份 | 恢复可校验、不重复统计、不复制凭据/安装身份 |
| 两端同时初始化/恢复同一目标；旧租约 worker 迟到 | 只有有效预留可 CAS 发布；另一任务不可覆盖，重试返回原结果 |
| 同 epoch 换机，旧操作已应用但 ACK 丢失，旧手机随后上线 | 新安装经授权对账，记录/活动各一次，凭据和安装身份不克隆 |
| 对象暂未上传后补齐 | 原操作进入依赖等待，补齐后同 ID 可成功，无永久拒绝回执 |
| 恢复来源缺文件且用户取消/重启 | 仅救援暂存可读，不发布可写协调库，不删除原来源 |
| 接近正文上限的中文及来源/活动快照 | 分块载荷可同步，业务整体提交一次，不被 HTTP 批次上限卡死 |

P0 用最小 fixtures 固定上述语义；P1/P2 以仿真客户端验证，P3/P4/P6 在 Android 实际持久化和真机生命周期上验证。未通过不能发布“完整多端同步”能力。
