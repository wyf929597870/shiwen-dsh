# Android parity for DSH and Shiwen menus

> 范围更新：Android 功能收敛方向见 [移动端精简范围](mobile-scope.md)。本文保留历史背景，其中要求移动端与桌面管理能力对齐的内容不再作为现行要求。


> **Current implementation status (2026-11-06):** The Android Settings UI now exposes node-bound Plugins, Automation tasks, and External access pages. These pages use the narrow `mobileManagement` owner API and native external-client wrappers described below; they do not implement general DSH Typert Remote, remote sessions, or Creator session setup. The earlier source inventory remains useful as an upstream reference, while the matrix near the end records the present mobile boundary.

This inventory uses the pinned local DSH source `0.2.2-alpha.3` and current Shiwen plugin source. It identifies real UI modules and service methods; it does not read user-installed profile/configuration data.

## Responsive UI versus native reuse

DSH Web's listed pages already have responsive layouts and can serve as visual/behavior references. Their React components are shipped as DSH Client plugins, not as Android native views. `android/native/.../NodeClient.kt` currently implements same-origin HTTP requests and cookie handling for auth/profile; it does not provide DSH Typert Remote streams. Therefore:

1. Shiwen Workbench calls (`agentState`/memory methods, external status/client CRUD, profile snapshot) can use the authenticated `/api/shiwen` HTTP route directly.
2. Android plugin and schedule management now use a fixed, owner-authenticated `mobileManagement` adapter on `/api/shiwen`, calling the verified Host service methods directly. The remaining preset roster/selection, Session events, approvals and DSH remote-access streams still need their own verified adapter or DSH Remote connection. No guessed REST endpoints are used.
3. The Web UI can be reused intact only when Android embeds the same DSH Web frontend and authenticates it as a DSH Client. For the current native UI, build native screens against the same typed Remote methods and preserve the existing Host-side execution and confirmation semantics.

## Access and state boundaries

DSH Remote requests go through `@deepseek-ai/dsh-api-gateway` and `remoteAccess`; the owner is always allowed, while a non-owner Peer receives only its configured method/resource grants. The original Plugins page is mounted only when `pluginManager/listBundles` is allowed. The schedule and preset APIs remain Host-owned. The exact Connection Fetch route `/api/shiwen` does not receive Typert's implicit method authorization. Its profile, Agent-memory, external-client and mobile-management methods therefore explicitly admit only the authenticated owner/browser Peer, including reads. The mobile-management adapter has a fixed action allowlist and dynamically resolves available Host services; an absent service does not prevent the rest of Workbench from starting.

This matrix inventories the upstream sources and reuse paths. It is not a claim of complete Android parity: plugin version updates/configuration, arbitrary presets, remote conversations/approvals, folded views and Creator remain outside the currently connected management pages. The concrete Android coverage is listed below.

## Current Android page and API boundary

| Android page | Current behavior | API and safety boundary |
| --- | --- | --- |
| Plugins | Lists bundles and plugin entries; searches configured market indexes with pagination; selects the declared default version/spec; installs with a stable install ID and process-local progress/cancel; enables/disables entries and removes eligible bundles. Typed `ChangeResult` outcomes distinguish applied, rejected, overridden, and restart-required states. | `nodeManagement({id,action,args})` over the owner-only `mobileManagement` allowlist. Each operation captures the visible node ID. Unknown write results lock further writes until explicit refresh and acknowledgment. |
| Automation tasks | Lists and opens task details and saved delivery history with paging; creates with all seven DSH timing forms; text-only edits preserve existing timing and destination; timing changes require an explicit opt-in. Pause/resume and delete use `expectedUpdatedAt`; manual run and destructive batch cleanup require confirmation. | `schedules.*` actions through `nodeManagement`; schedule result codes such as `schedule_conflict`, `schedule_not_found`, and `schedule_execution_pending` remain visible and do not clear the editor as success. Manual run explicitly warns that it starts a real model task. |
| External access | Shows bridge state and client metadata; selects only `read`, `create`, `update`, and `delete` scopes; creates credentials through a native secure dialog; confirms revocation. | `nodeExternalStatus`, `configureExternalClient`, `nodeExternalRevoke`. The token is never returned to JS. If native confirms the credential was not displayed, the page tells the user to revoke it and create a replacement. Endpoint is server-side and may not be directly reachable from a phone. |
| More | Links to existing local chat/materials and the active node's Plugins, Automation, and External access pages. Remote Creator is called out as unavailable. | Does not claim to create remote DSH sessions, show folded DSH views, or invoke a generic Typert Remote client. |

On every management response, `nodeChanged: true` means the request remained bound to the original node while its configured address changed. The page reports that the result belongs to the original service, stops automatic reads, and blocks writes until the service state is explicitly reviewed. It never silently follows the currently selected node.
